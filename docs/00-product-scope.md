# 产品需求与 V1 边界

## 要解决的问题

将网关历史日志与在线 Agent 执行转换为统一、可追溯的记录，回答：哪个版本在哪些样本失败、失败证据是什么、修改后是否回归、质量提升付出了多少时间与成本。

主要用户是个人开发者、Agent 应用开发和质量工程人员。项目用于实际开发与面试展示，技术复杂度由需求驱动，不能把尚未实现的能力写成简历成果。

## 必须完成的流程

| 用户目标 | 输入 | 输出与验收 |
| --- | --- | --- |
| 管理评测对象 | Agent 配置与版本 | 草稿可编辑；发布后生成不可变快照 |
| 管理测试集 | JSONL 样本 | 可发布数据集版本；case_key 在版本内唯一 |
| 在线实验 | 已发布数据集、Agent、方案版本 | 样本×对象×重复编号生成 Run，Mock 可端到端运行 |
| 离线实验 | JSONL 历史执行记录 | 逐行校验、错误定位、幂等导入、统一评测 |
| 定位失败 | Trace、输出、结果 | 能从报告进入样本和事件证据，缺失信息明确展示 |
| 人工复核 | 算子结果或 Run | 领取、提交、审核、退回，历史可追溯 |
| 版本回归 | 同数据集/方案的对象 | 同样本配对差异、缺失覆盖率、成本与耗时 |

## 交付阶段

1. 基础：TASK-001~003，工程对齐、模型/API 基础、版本管理。
2. 最小闭环：TASK-004~007，Mock 在线运行、离线导入、轨迹、规则评测。使用数据库轮询领取；必须已具备租约、幂等与超时回收。
3. 质量闭环：TASK-008~010，LLM Judge、人工复核、实验报告与回归门禁。
4. 可靠性增强：TASK-011，在既有任务协议上增加 Outbox/RabbitMQ 与故障演练；TASK-012 只根据真实基线做性能优化。

## V1 不做

多租户、完整组织权限、计费、余额、秒杀、短链、微服务拆分、任意代码的生产安全沙箱、自动训练、通用 DAG 平台、自建 Langfuse 的全套观测能力。不默认引入 ClickHouse、Redis 或分布式事务。

## 演示数据与性能

提交不少于 10 个样本、2 个 Mock Agent 配置、1 个规则方案、至少 1 个可解释失败与 1 个回归样本；这些是功能演示数据，不是性能结论。性能数值在 TASK-012 记录硬件、样本规模、数据大小、并发和原始结果后填写，设计阶段不预填“降低 90%”等指标。

## 前提

本地单租户可用测试身份做标注，但界面必须标识开发模式。若要公网使用，必须另立鉴权与授权任务；共享 Worker token 不能替代用户系统。真实代码 Runner 只运行可信仓库与可信测试，具备目录、超时、进程清理和资源限制；不能宣传为已具备强安全隔离。
